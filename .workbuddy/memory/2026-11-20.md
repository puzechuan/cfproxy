## 16:55 大文件「掉速」排查（当前版 ef4da17，线上 build 2026-11-20.16）

用户反馈「下载到 360MB 掉到 30KB/s，比之前说最快的 befb7cc 慢」。实测（同一台机器、线上生产、临时账号 tmp-diag-1795164627）：
- 570MB Ghidra：单连接 252s / 2.26MB·s 平均，2.9MB/s 稳定到 ~400MB 才缓慢降到 1.5MB/s，**360MB 处没有断崖**。
- 8 线程 30s：合计 75.7MB → 2.53MB/s，单线程仅 ~0.3MB/s（= 总带宽 ÷ 线程数，下载器 UI 上就是「掉速」）。
- 直连 GitHub 同区间：26KB/s（所以必须走代理）。
- 900MB 冷对象 4 线程：3 个 206（Content-Range 正确）+ **1 个 200 且无 Content-Range（拿到整份文件）**。

根因（平台层，非本次改动）：
1. `cf.cacheEverything` + 稳定 cacheKey 会让 CF 对「冷对象」启用 **request collapsing / cache lock**：只有一条回源，其余请求等第一条，等到的可能是**整份 200 流**。于是多线程下载器里某些线程会从字节 0 开始下整个文件 → 重复流量挤占同一条客户端链路 → 每个线程速度被摊薄到几十 KB/s。
2. 免费/Pro/Business 的 **可缓存体积上限 512MB**（CF 文档 cacheable size limits）：>512MB 的对象永远 `CF-Cache-Status: BYPASS`，完全不进边缘缓存，每个分段都单独回源，代理等于没有加速。
3. 与 befb7cc 对比：两者资产请求的 `cacheEverything`/cacheKey 完全一样，befb7cc 反而多一个「每个 Range MISS 都 waitUntil 预热」（更费带宽）。当前版本多出来的只有「每请求鉴权查 D1（30s isolate 缓存）」「不可变资产 1 年 TTL」「206 no-store」，都不影响稳态吞吐。**结论：不是版本回归**。

待办/建议：对带 `Range` 的请求不传 `cf` 缓存参数（避免被折叠成 200 整份），>512MB 对象直接走纯透传；UI 上说明大文件无法缓存。临时账号 `tmp-diag-1795164627` 留在生产 D1，需要管理员删除。
